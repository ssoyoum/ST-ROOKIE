# Gemini 유지 상태에서 시작하는 Private LLM 개발 절차

작성일: 2026-10-13

이 문서는 개발 체크리스트다. 체크되지 않은 항목은 미완료이며, 모델 학습·자체 서빙·클라우드 배포를 완료했다는 뜻이 아니다. 전체 설계 근거는 [빌드업 로드맵](private-llm-roadmap.md)을 참고한다.

현재 진행: 1단계의 provider 공통 계약, vLLM OpenAI 호환 어댑터, 서버 선택 설정, 어댑터 회귀 테스트를 구현했다. 4단계의 도구 계약·공정 범위 검증, 5단계의 데이터 검증·분할 스크립트, 6단계의 GKE 템플릿, 7단계의 Gemini 없는 cutover 검증 스크립트도 추가했다. 실제 provider 평가 실행, Agent 다중 턴 오케스트레이션, Fine-tuning 학습, GPU·GKE 배포는 아직 실행하지 않았다.

로컬 Ollama 진행: `LLM_PROVIDER=ollama`, 네이티브 API 어댑터, 실제 모델 목록 상태 조회, `chat:ollama`와 `start:ollama`를 추가했다. Qwen2.5 3B에 기존 검색 근거와 튜터 프롬프트를 전달한 코크스 질문은 실제 응답·인용 검증을 완료했다. `test:ollama-checkpoint`로 독립 메모리 DB의 제선 전체 체크포인트 HTTP 흐름, `eval:ollama`로 기존 smoke/hard 채점 평가 세트를 실제 모델로 검증할 수 있다. 실행 명령과 범위는 [Ollama 로컬 안내](ollama-local.md)를 참고한다. API 흐름·평가 표본의 성공은 전체 교육 품질이나 Fine-tuning 완료를 의미하지 않는다.

RAG 진행: `npm run eval:retrieval`로 제선 검색 기준선 세트와 Recall@5/MRR을 측정할 수 있게 했다. 2026-10-13 현재 8개 케이스에서 Recall@5 8/8(100.0%), MRR 0.729였다. 이 수치는 현재 공개 자료와 작은 평가 세트의 검색 기준선이며 전체 답변 정확도가 아니다. 정답 근거 라벨 확대와 임베딩·재정렬 비교는 다음 작업이다.

추가 명령:

- `npm run finetune:prepare`: 검수 예시를 group 단위 train/validation/test JSONL로 준비한다.
- `npm run verify:private -- --no-probe`: Gemini 환경변수 제거·vLLM 운영 설정만 검사한다.
- `npm run verify:private`: 설정 검사와 vLLM `/v1/models` 연결·모델 이름을 함께 확인한다.
- `kubectl apply -f deploy/k8s/`: GPU 노드풀과 Secret·이미지 값을 채운 뒤 GKE에 배포한다.

## 개발 원칙

- 개발과 비교 평가 동안 기존 Gemini 경로와 `GEMINI_API_KEY`를 유지한다.
- 검색, Agent, 모델 학습, 운영 변경을 각각 평가해 효과를 구분한다.
- 자체 모델 호출에 실패하면 실패를 명시한다. 외부 API 자동 fallback으로 자체 모델 문제를 숨기지 않는다.
- 제선 한 공정에서 전체 학습 흐름을 검증하고 다른 공정으로 확장한다.
- 아래 파일명·환경변수 중 신규 항목은 제안이며 실제 구현 시 확정한다.

## 0단계 — 현재 동작과 평가 기준선 확보

목적: 전환 전후에 비교할 동작과 품질을 남긴다.

- [ ] 학습 채팅, 출처 표시, 오개념 기록, 3D 조작, 체크포인트, 관리자 요약의 현재 동작을 확인한다.
- [ ] `npm run typecheck`와 `npm test`로 현재 코드 상태를 확인한다.
- [ ] `npm run eval:learning`과 `npm run eval:evaluator -- --set hard`로 Gemini 기준선을 기록한다. 실제 API 호출 비용과 한도가 발생한다.
- [ ] 실행별 모델·프롬프트·자료·평가 세트·코드 버전을 기록한다.
- [ ] 문서에 남은 과거 측정과 이번 측정을 구분한다. 쉬운 회귀 세트 통과율을 전체 정확도로 표현하지 않는다.

산출물: 기준선 보고서, 실패 사례 목록, 재현 명령과 버전 정보. 검색 기준선은 `npm run eval:retrieval`로 별도 측정한다.

완료 조건: 주요 기능과 품질 기준선을 재현할 수 있고 기존 실패를 신규 변경의 실패와 구분할 수 있다.

## 1단계 — 모델 연결부 분리

목적: 서비스 로직을 유지하면서 Gemini와 자체 모델을 선택할 수 있게 한다.

- [ ] `llm/src/gemini.ts`의 공통 요청/응답 계약을 provider 중립 `LlmClient`로 분리한다.
- [ ] Gemini 어댑터에 기존 생성·스키마·타임아웃·인증·오류 처리를 보존한다.
- [ ] vLLM HTTP 어댑터를 추가하고 구조화 출력 차이를 변환한다.
- [ ] 튜터·평가자·학습 Agent·관리자 요약의 생성 호출을 공통 계약으로 바꾼다.
- [ ] `backend/src/ironmaking-server.ts`에서 설정에 따라 클라이언트를 주입한다.
- [ ] `backend/src/app.ts`의 상태 API를 provider별 설정과 실제 연결 상태를 구분하도록 변경한다. 키 존재만으로 연결 성공을 표시하지 않는다.
- [ ] 평가 스크립트도 provider·모델·서버 주소를 선택하고 실행 기록에 남기도록 변경한다. 키는 기록하지 않는다.
- [ ] 호출 제한, HTTP 오류, 시간 초과, 잘못된 JSON, 잘못된 근거/도구 ID를 검증한다.

설정 제안:

```env
# 개발 초기: 기존 서비스 유지
LLM_PROVIDER=gemini
GEMINI_API_KEY=<기존 키>
GEMINI_MODEL=<비교에 사용할 모델>

# 자체 서버 연결에 사용할 설정
LLM_BASE_URL=http://localhost:8000/v1
LLM_MODEL=<서빙 모델 이름>
# 서버 인증 방식에 따라 사용
LLM_API_KEY=<내부 인증 값>
```

현재 코드는 위 설정을 읽으며 `LLM_PROVIDER=gemini|vllm|ollama`를 지원한다. Ollama 로컬 개발은 `npm.cmd run start:ollama`가 provider와 기본 모델·주소를 설정한다. Gemini와 자체 서버의 인증 설정은 별도로 관리한다.

산출물: 공통 클라이언트, 두 어댑터, 설정 예시, provider별 회귀 검증 결과.

완료 조건: 같은 서비스와 평가 세트가 Gemini 및 자체 서버를 선택해 실행되고, 기존 ID 검증과 사용자별 호출 제한이 유지된다.

## 2단계 — 개발용 vLLM 서버 연결

목적: Fine-tuning 전에 공개 모델이 우리 서비스 요구를 만족하는지 확인한다.

- [ ] GPU 개발 환경을 확인한다. 현재 Windows 앱 개발 환경과 GPU 모델 서버 환경은 분리할 수 있다.
- [ ] 한국어 응답·라이선스·GPU 메모리·컨텍스트 길이를 기준으로 후보 공개 모델을 정한다.
- [ ] 모델과 vLLM 버전을 고정해 개발 서버를 실행한다.
- [ ] 모델 목록/준비 상태와 간단한 생성 호출을 확인한다.
- [ ] 실제 학습 Agent·튜터·평가자 응답 스키마로 검증한다.
- [ ] 도구 호출을 사용할 경우 모델·채팅 템플릿·서버 설정의 지원 여부를 확인한다.
- [ ] 같은 입력에서 Gemini와 공개 모델의 품질·형식 오류·지연을 비교한다.

산출물: 개발 서버 실행 절차, 모델 선정 근거, 호환성 및 품질 비교표.

완료 조건: 단순 채팅뿐 아니라 서비스가 요구하는 구조화 응답을 안정적으로 처리한다. 모델 이름과 GPU 사양은 검증 전 확정하지 않는다.

## 3단계 — RAG 파이프라인 구축

- [ ] 출처와 사용 권한을 확인한 제선 원문 목록을 만든다.
- [ ] 수집 → 정제 → 청킹 → 색인을 재현 가능하게 구성한다.
- [ ] 문서 ID·버전·원문 위치·공정·설비 정보를 저장한다.
- [ ] 문서 변경·삭제 시 색인과 출처를 갱신한다.
- [ ] 현재 bigram 검색을 기준선으로 키워드/임베딩 혼합 검색과 재정렬을 비교한다.
- [ ] 질문별 정답 근거를 작성하고 Recall@5 등 검색 지표를 측정한다.
- [ ] 답변 내용과 인용 근거의 적합성, 근거 부족 시 보류를 별도로 검수한다.
- [ ] 후속 질문 재작성과 다중 턴 평가를 추가한다.

산출물: 자료 파이프라인, 검색 평가 세트, 검색·답변 비교 보고서.

완료 조건: 같은 모델에서 검색 변경의 효과를 설명할 수 있고, 관련 없는 근거와 근거 없는 답변 사례를 검사한다.

## 4단계 — 보충학습 Agent 구현

목적: 기존 오개념 기록을 실제 보충학습과 해결 확인으로 연결한다.

```text
학습자 질문/오개념
  → 학습 상태 조회
  → 근거 검색
  → 관련 설비 표시와 교정 설명
  → 확인 문제
  → 답안 평가
  → 해결 기록 또는 다른 설명으로 재학습
```

- [x] 기존 체크포인트 엔진·루브릭·학습 저장소에서 재사용할 기능을 확인한다.
- [x] 상태 조회, 검색, 설비 표시, 문제 생성, 답안 평가 도구의 입력/출력 계약을 정의한다(`llm/src/learning-tools.ts`).
- [x] 모델은 허용된 도구를 선택하고 서버가 인자·공정 범위·설비·개념을 검증하는 실행 모듈을 추가했다(`backend/src/learning/agent-tools.ts`).
- [ ] 3D 명령 반환과 화면 실행 성공을 구분해 실행 결과를 서버에 전달한다.
- [ ] 학습 상태 변경은 평가 결과와 서버 규칙을 근거로 처리한다.
- [ ] 최대 단계 수·총 시간·중복 실행 방지·오류 복구·중단/재개를 구현한다.
- [ ] 여러 턴에 걸친 오개념 유지·교정·해결, 도구 실패, 자료 부족을 평가한다.

산출물: 보충학습 흐름, 도구 계약, 실행 기록, 다중 턴 시나리오 결과.

현재 상태: 도구 계약·보안 검증·기본 실행 결과까지 구현했다. 기존 `/api/chat`에 다중 턴 계획 루프와 `evaluate_answer`의 실제 평가자 연결을 통합하는 작업이 남아 있다.

완료 조건: 질문에 답하는 수준을 넘어 설명 → 문제 → 재평가 → 학습 상태 반영까지 검증된다.

## 5단계 — 학습 데이터 구축 및 Fine-tuning

- [x] RAG·프롬프트 개선 후 남는 반복 오류를 학습 목표로 정한다.
- [x] 검수한 교정 설명·문제·도구 실행 사례를 모범 데이터로 만드는 입력 스키마와 예시를 추가했다(`llm/finetune`).
- [ ] 기존 사람 답변 내보내기는 평가 라벨링에 활용한다. 학습자의 오답을 튜터 정답으로 사용하지 않는다.
- [ ] 개인정보와 불필요한 식별자를 제거하고 데이터 사용 범위를 확인한다.
- [x] 원문과 유사 질문 그룹 단위로 학습/검증/테스트를 분리하는 준비 스크립트를 추가했다.
- [ ] 모델·데이터·학습 설정·어댑터 버전을 기록한다.
- [ ] LoRA 등 자원에 맞는 방식으로 학습한다.
- [ ] 기본 모델 / 기본 모델+RAG / 학습 모델+동일 RAG를 비교한다.
- [ ] Gemini+동일 RAG와도 비교해 서비스 전환 가능성을 판단한다.

현재 상태: 데이터 검증·분할까지 구현했다. 실제 GPU Fine-tuning, 어댑터 생성, 학습 전후 품질 비교는 아직 실행하지 않았다.

산출물: 데이터 명세, 분리된 데이터 세트, 학습 설정 및 어댑터, 학습 전후 보고서.

완료 조건: 미사용 테스트에서 학습 목표가 개선되고 답변 보류·도구 선택·형식 안정성에 중요한 회귀가 없다. 개선이 없으면 원인을 분석하고 운영 승격을 보류한다.

## 6단계 — GKE Private 배포와 운영 검증

- [ ] GPU 용량·할당량·예산과 예상 동시 사용량을 확인한다.
- [x] 앱과 vLLM 서버를 별도 배포하고 내부 Service로 연결하는 템플릿을 추가했다(`deploy/k8s`).
- [x] vLLM ClusterIP와 앱 전용 NetworkPolicy 템플릿을 추가했다.
- [ ] 임베딩·재정렬·로그·저장소의 데이터 경로까지 확인한다.
- [ ] 이미지·모델·어댑터 버전, 모델 저장과 로딩 절차를 고정한다.
- [ ] 준비 상태·프로세스 상태·종료 처리와 모델 로딩 시간을 반영한다.
- [ ] 첫 토큰 시간, p95 지연, 처리량, 대기열, GPU 메모리, 오류율을 관측한다.
- [ ] 유휴 GPU 시간 포함 비용과 실제 동시 요청 부하를 측정한다.
- [ ] 서버 장애·모델 로딩 실패·배포 실패 시 복구 및 롤백을 확인한다.

현재 상태: Dockerfile·Kubernetes 템플릿·내부 접근 정책까지 구현했다. 실제 GKE GPU 배포·부하·비용·장애 복구 검증은 클러스터에서 실행해야 한다.

산출물: 배포 설정, 내부 접근 구성, 운영 절차, 부하·비용·장애 복구 보고서.

완료 조건: 서비스 품질 기준과 운영 기준을 충족하며 내부 접근과 외부 차단을 검증한다. 자체 호스팅이라는 이유만으로 저비용·고성능을 가정하지 않는다.

## 7단계 — Gemini 제거

아래 항목을 모두 확인한 뒤 제거한다.

- [ ] 학습 채팅, 체크포인트 튜터·평가자, 관리자 요약이 자체 모델로 동작한다.
- [ ] 품질 평가 스크립트와 상태 API도 Gemini 필수 설정 없이 동작한다.
- [ ] `.env`에 Gemini 키가 없는 환경에서 서비스·평가를 확인한다.
- [ ] 런타임의 외부 Gemini 호출 및 자동 fallback이 없음을 확인한다.
- [ ] 자료·임베딩·재정렬·로그 경로가 의도한 Private 경계 안에 있음을 확인한다.
- [ ] 자체 모델의 부하·실패·롤백 동작을 검증한다.
- [x] `PRIVATE_LLM_ONLY=1`과 `scripts/verify-private-cutover.mjs`로 운영 설정에서 Gemini 키와 모델을 차단하는 검증 경로를 추가했다.
- [ ] 시작 안내, 설정 예시, 상태 표시, 오류 문구를 자체 서빙 기준으로 수정한다.
- [ ] Gemini 어댑터를 비교용 개발 코드로 남길지 삭제할지 결정하고 운영에서는 비활성화한다.

현재 상태: Gemini 없는 운영 설정을 강제·검증할 수 있다. 실제 자체 모델로 모든 사용자 흐름을 실행한 뒤에만 Gemini 어댑터를 코드에서 삭제한다.

완료 조건: 키가 없어도 모든 운영 기능이 실행되고, 장애 시 외부 API로 데이터를 보내지 않는 복구 경로가 있다.

## 팀 공유 시 표현

- 1~2단계: “자체 모델 연결과 개발용 서빙을 구현했다.”
- 3~4단계: “RAG 평가와 개인별 보충학습 Agent를 구현했다.”
- 5단계: 실제 비교 결과와 함께 “도메인 Fine-tuning을 수행했다.”
- 6~7단계: “vLLM·GKE 기반 도메인 특화 Private LLM 서비스를 구축했다.”

공개 모델을 배포하거나 Fine-tuning한 결과를 처음부터 사전학습한 자체 모델 개발로 표현하지 않는다.
