# ST-ROOKIE 도메인 Agent·Private LLM 빌드업

작성일: 2026-10-13. 현재 저장소를 근거로 작성한 구현 계획이며, 아래 신규 기능·배포·학습은 아직 구현하거나 실행하지 않았다.

개발 착수부터 Gemini 제거까지의 실행 체크리스트는 [Private LLM 개발 절차](private-llm-development.md)를 참고한다.

## 팀에 설명할 목표

현재 Gemini 기반 철강 공정 교육 MVP를, 근거 검색 품질을 측정할 수 있고 학습자의 오개념에 따라 보충학습을 수행하는 도메인 Agent로 발전시킨다. 이후 공개 모델을 동일 조건에서 비교하고 Fine-tuning한 뒤 vLLM·GKE 내부 서빙으로 전환한다.

RAG는 답변에 사용할 지식을 공급하고, Agent는 학습 절차와 도구 실행을 결정하며, Fine-tuning은 설명·교정·도구 선택 행동을 개선한다. Private 서빙은 추론 인프라와 데이터 경로를 직접 통제한다. 각 단계의 효과는 따로 측정해야 한다.

## 현재 구현으로 확인한 근거

| 확인 위치 | 현재 동작 | 다음 단계가 필요한 이유 |
|---|---|---|
| `llm/src/retrieval.ts` | 한국어 bigram 겹침, 용어집 확장, 화면 설비 가중치, 상위 5개 검색. section.md가 없으면 제선 공개 자료 메모 사용 | 표현이 다른 질문·긴 문서에 대한 검색 품질을 측정하고 개선할 필요가 있음 |
| `llm/src/learning-agent.ts` | 단일 답변 생성 중심. JSON 검증, 허용된 근거·개념·화면 ID 필터링, 화면 조작 정규화 | 도구 실행 결과를 받아 재검색·재학습하는 절차가 필요함. 허용된 근거 ID라는 사실만으로 답변 내용이 입증되지는 않음 |
| `backend/src/learning/routes.ts` | 최근 대화 6턴·미해결 오개념 전달. 검색 결과가 없을 때 직전 대화를 붙여 재검색 | 관련 없는 근거가 일부 검색되면 지시어 해석이 개선되지 않음. 후속 질문 재작성과 다중 턴 평가가 필요함 |
| `llm/eval/run-learning.ts` | 상태·화면 조작·오개념·선택적 단어 포함 검사. 평가 입력의 history와 openMisconceptions는 빈 배열 | 실제 개인화·연속 학습 흐름과 문장별 근거 적합성을 추가 평가해야 함 |
| `llm/eval/README.md` | smoke/hard 분리, 실제 사람 답변 익명화 내보내기, 블라인드 정답 라벨링 | 검수 데이터 구축의 출발점이 있음. 사용자 답변을 그대로 튜터의 모범 출력으로 학습하면 안 됨 |
| `backend/src/ironmaking-server.ts` | 학습 Agent·튜터·평가자·관리자 요약이 GeminiClient를 사용 | 모든 호출 경로를 전환해야 Gemini 키를 제거할 수 있음 |
| `backend/src/app.ts` | 연결 상태가 Gemini 키와 모델 설정에 종속 | 자체 서버 상태 확인으로 바꿔야 함 |

`docs/learning-mode.md`의 51/51 등은 기존 문서에 기록된 특정 세트의 1회 측정이다. 이번에 재실행한 결과가 아니며, 전체 도메인 정확도나 개인화 Agent 성능으로 일반화하지 않는다.

## 구현 순서와 완료 기준

### 1. 평가 기준선과 모델 연결부 분리

- 기존 Gemini 평가를 기록하고 데이터·프롬프트·모델·검색 설정 버전을 함께 보존한다.
- provider 중립 `LlmClient`와 Gemini/vLLM 어댑터를 구성한다. 기존 JSON 검증과 ID 제한은 유지한다.
- 튜터·평가자·학습 Agent·관리자 요약·평가 스크립트·상태 API를 공통 연결부로 전환한다.
- 타임아웃·인증·사용량 제한·오류 분류 및 구조화 출력 차이를 어댑터에서 처리한다.
- 완료: 기존 기능 회귀 확인, 자체 서버 연결 확인, provider별 실패 경로 확인. vLLM 모델은 우선 학습 전 공개 모델로 연결 가능하다.

왜 먼저 하는가: 이후 RAG와 Agent를 구현할 때 특정 모델 API에 다시 묶이지 않고 같은 평가를 재사용할 수 있다.

### 2. RAG 수집·검색·평가 구축

- 사용 허가와 출처가 확인된 원문으로 수집 → 정제 → 청킹 → 색인을 구성한다.
- 문서 ID·버전·원문 위치·공정·설비·출처를 보존하고 수정 시 재색인한다.
- 현 검색 / 키워드 검색 / 임베딩과 키워드 혼합 / 재정렬 추가를 같은 질문에서 비교한다.
- 질문별 정답 근거를 라벨링해 Recall@5와 순위 품질을 측정한다. 답변 정확성·근거 적합성·보류 적절성은 별도 검수한다.
- 다중 턴의 지시어 질문, 자료에 없는 질문, 유사하지만 잘못된 근거도 포함한다.
- 완료: 기준선 대비 개선 보고서와 재현 가능한 평가 명령. 목표 수치는 기준선 측정 후 합의하며 현재 임의의 정확도를 보장하지 않는다.

왜 필요한가: 검색 실패와 모델 생성 실패를 구분하지 않으면 Fine-tuning할 대상을 잘못 선택하게 된다.

### 3. 개인별 보충학습 Agent

도구 후보: `get_learning_state`, `search_materials`, `show_equipment`, `create_quiz`, `evaluate_answer`.

흐름: 오개념 확인 → 근거 검색 → 설비 표시 → 교정 설명 → 확인 문제 → 답안 평가 → 이해 시 해결 기록 / 미이해 시 다른 설명과 재평가.

- 기존 체크포인트·루브릭·학습 기록을 재사용한다.
- 화면 명령 반환과 실제 실행 성공을 구분하고 프런트엔드 확인 결과를 기록한다.
- 도구 인자와 사용자별 권한을 서버에서 검증한다. 학습 상태 변경은 평가 결과를 근거로 서버가 수행한다.
- 최대 단계 수·총 시간·중복 실행 방지·실패 복구·중단 및 재개 상태를 둔다.
- 완료: 다중 턴 시나리오에서 도구 선택, 실행 성공, 오개념 해결 판정, 실패 복구를 평가하고 실행 기록으로 재현한다.

왜 필요한가: 기존 답변·화면 조작 기능을 학습 결과까지 이어지는 서비스 동작으로 확장할 수 있다. 여러 Agent를 먼저 만드는 것보다 하나의 학습 절차를 검증하는 것이 범위를 명확히 한다.

### 4. 도메인 Fine-tuning

- RAG·프롬프트 개선 후에도 반복되는 교정·설명·도구 선택 오류를 학습 목표로 정한다.
- 검수한 튜터 응답·도구 실행 사례를 학습 데이터로 만든다. 사용자 개인정보·불필요한 식별자는 제거한다.
- 문서와 유사 질문 그룹 단위로 학습/검증/테스트를 분리하고 테스트는 학습에 사용하지 않는다.
- 공개 모델에 LoRA 기반 학습을 우선 검토하되 한국어 품질·라이선스·GPU 자원으로 모델과 학습 방식을 결정한다.
- 비교: 공개 기본 모델 / 기본 모델+RAG / Fine-tuning 모델+동일 RAG. Gemini+동일 RAG는 서비스 기준선으로 추가한다.
- 완료: 정확성·교정 품질·도구 선택·구조화 출력·보류 행동 및 지연 측정. 개선되지 않으면 학습 모델을 운영에 승격하지 않는다.

왜 필요한가: 학습했다고 좋아졌다고 주장하는 대신 동일 조건에서 개선을 입증하기 위해서다.

### 5. vLLM·GKE Private 서빙과 운영

- GPU 환경에서 모델·컨텍스트 길이·구조화 출력·도구 호출을 검증한 뒤 GKE에 배포한다.
- 앱과 모델 서버를 분리하고 내부 서비스 연결, 인증, 네트워크 접근 제한을 구성한다.
- 임베딩·재정렬·로그·저장소까지 데이터가 흐르는 위치를 확인한다. Private 운영에서는 외부 Gemini 자동 fallback을 기본으로 두지 않는다.
- 컨테이너·모델·어댑터 버전 고정, 모델 로딩 준비 상태, 배포/롤백 절차, GPU 메모리·대기열·오류 관측을 구성한다.
- 첫 토큰 시간, p95 지연, 처리량, GPU 메모리, 유휴 시간 포함 비용을 실제 동시 요청으로 측정한다.
- 완료: 내부 접근과 접근 차단 확인, 부하·장애·롤백 검증, 전체 호출 경로의 Gemini 의존 제거 확인.

왜 마지막 운영 단계로 두는가: 자체 호스팅이 품질이나 비용 우위를 자동 보장하지 않는다. 모델 적합성과 수요를 확인한 후 운영 구성을 정해야 한다. 로컬/개발용 vLLM 연결은 1단계부터 진행할 수 있다.

## 환경변수 전환안

아래는 구현 예정 규약이며 현재 바로 사용할 수 있는 설정이 아니다.

```env
LLM_PROVIDER=vllm
LLM_BASE_URL=http://llm-server:8000/v1
LLM_MODEL=steel-tutor
LLM_API_KEY=<내부 인증 방식에 맞는 값>
```

서버 주소·모델 이름은 예시다. 실제 인증 방식에 따라 키 사용 여부를 정한다. 전환 비교 기간에는 Gemini 키를 유지할 수 있지만, 모든 기능과 평가 경로를 자체 모델로 바꾼 뒤 Private 운영 설정에서 제거한다. 환경변수·토큰 값은 저장소에 커밋하지 않는다.

## 역할별 병행 가능한 작업

| 담당 영역 | 산출물 |
|---|---|
| 데이터·RAG | 원문 목록, 정제/청킹 파이프라인, 정답 근거 세트, 검색 비교 보고서 |
| 백엔드·Agent | 공통 모델 연결부, 도구 계약, 학습 상태 전이와 실행 기록 |
| 프런트엔드 | 설비 조작 실행 확인, 보충학습 진행/재개 화면 |
| 모델·평가 | 검수 모범 데이터, 분리 기준, 학습 전후 비교 보고서 |
| 인프라 | GPU 서빙 검증, GKE 배포 설정, 접근 제어, 부하·비용·복구 보고서 |

이는 역할 구분 제안이며 실제 인원이나 일정 배정은 아니다. 먼저 제선 한 공정에서 전체 흐름을 검증한 뒤 제강·연주·압연으로 확장한다.

## 팀 공유용 설명

“현재는 Gemini로 근거 답변과 3D 조작을 제공하는 교육 MVP입니다. 다음 단계에서는 검색과 답변 품질을 분리해서 측정하고, 오개념을 설명·문제·재평가까지 이어주는 보충학습 Agent를 만들겠습니다. 그 과정에서 검수한 데이터를 모아 공개 모델을 Fine-tuning하고, 같은 평가로 개선을 확인한 뒤 vLLM·GKE 내부 서빙으로 전환하겠습니다. 최종 결과는 도메인 특화 Private LLM 서비스이며, 처음부터 사전학습한 자체 모델 개발과는 구분합니다.”

## 외부 기술 근거

- [vLLM OpenAI 호환 서버](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/): 자체 모델을 HTTP API로 제공할 수 있다. API 호환만으로 Gemini 요청·스키마가 그대로 호환되는 것은 아니므로 어댑터 검증이 필요하다.
- [Hugging Face PEFT LoRA](https://huggingface.co/docs/peft/en/package_reference/lora): 공개 모델을 도메인에 맞게 적응시키는 파라미터 효율적 학습 방식의 근거.
- [GKE GPU·vLLM 배포](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/serve-llama-gpus-vllm): GPU 기반 모델 서빙 배포의 공식 구현 참고. 예제 모델·GPU를 그대로 프로젝트 선택으로 확정하지 않는다.
- [GKE 자체 모델과 Agent 연결](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/agentic-adk-vllm): 앱과 자체 모델 서버를 분리하고 내부 서비스 API로 연결하는 아키텍처 참고. ADK 도입은 필수 조건이 아니다.
